# Wesnoth engine compatibility at ticket planning

The coordinator checks game-content designs **before creating a worktree or
invoking an implementation worker**. A fresh ticket under
`addons/Star_Wars_Thrawn_Trilogy/` must supply a versioned
`compatibility_review`. The Sol single-ticket and backlog planners receive the
same area catalog. Python validates the matrix again when selecting a stored
ticket and when loading its execution contract. Tester and reviewer receive the
planned constraints and compare them with the changed code.

The catalog covers every game-design surface, not only movement:

| Area | Start with the official reference | Typical pre-code question |
| --- | --- | --- |
| Campaign registration and flow | [CampaignWML](https://wiki.wesnoth.org/CampaignWML) | Is the campaign define, first scenario, and include structure supported? |
| Scenario objectives | [ScenarioWML](https://wiki.wesnoth.org/ScenarioWML) | Is the win/lose condition implemented by an engine event? |
| Maps and terrain | [TerrainCodesWML](https://wiki.wesnoth.org/TerrainCodesWML) | Are terrain codes and route costs valid for the target build? |
| Units and movement | [UnitsWML](https://wiki.wesnoth.org/UnitsWML) | Does the actual movetype and movement budget support the design? |
| Combat and abilities | [AbilitiesWML](https://wiki.wesnoth.org/AbilitiesWML) | Does the proposed attack/special/ability act in the intended combat phase? |
| Events and state | [EventWML](https://wiki.wesnoth.org/EventWML) | Are trigger filters, event ordering, and variable lifetimes correct? |
| AI and recruitment | [Wesnoth AI Framework](https://wiki.wesnoth.org/Wesnoth_AI_Framework) | Can the side recruit and does the AI receive the intended goals? |
| Lua and macros | [LuaAPI](https://wiki.wesnoth.org/LuaAPI) | Is the API available in this engine generation and correct context? |
| Presentation and assets | [AnimationWML](https://wiki.wesnoth.org/AnimationWML) | Are image/audio references and animation tags supported and present? |
| Saves and transitions | [ScenarioWML](https://wiki.wesnoth.org/ScenarioWML) | Does `next_scenario`, carryover, recall, and save state follow the intended route? |
| Multiplayer synchronization | [ReferenceWML](https://wiki.wesnoth.org/ReferenceWML) | Could this code run in a synchronized game, and is its state deterministic? |
| Other engine rules | [ReferenceWML](https://wiki.wesnoth.org/ReferenceWML) | Does the feature touch economy, visibility, time of day, progression, localization, or another engine area not listed above? |

For each area, the planner records either `checked` with a concrete documented
constraint, compatible design, source or installed-core pre-code check, and
focused later runtime check; or `not_affected` with a specific reason. Python
requires all areas, at least one checked area, and a checked area matching
obvious path classes such as scenarios, units, Lua, maps, campaign registration,
and assets. An `experiment` is rejected from unattended implementation until a
separate bounded engine spike and reviewed design decision exist. A planner
cannot turn unsupported behavior into an accepted exception by writing prose.

For version-specific behavior, inspect the installed Wesnoth 1.19/1.20 engine's
core WML, terrain definitions, unit movetypes, macros, and schema. The official
[ReferenceWML](https://wiki.wesnoth.org/ReferenceWML) itself cautions that a
wiki page may be incomplete or slightly inaccurate. A citation and completed
matrix prevent avoidable design mistakes but do not establish that a scenario
loads or behaves correctly. Existing static validation, installed-engine
preprocessing, scoped behavior probes, GUI launch qualification, tester, and
independent reviewer remain separate gates. A `not_affected` claim is reviewable
and must be corrected if the actual diff changes that area.

Existing resumed or exact-PR replacement tickets retain their original
immutable contract. The two
legacy automatic repair paths for a failed published game or historical sweep
can still dispatch a bounded correction from an observed engine diagnostic;
they do not claim to have a new pre-code design review. A new design ticket,
including one generated by autonomous backlog refill, must have the review.

Run `python3 agent/coordinator/engine_compatibility_selftest.py` and
`python3 agent/dashboard/test_dashboard.py` for the planning and dispatch
controls. The pre-code gate is structural and deliberately does not invent a
complete WML semantic validator.
